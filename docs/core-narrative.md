# 医学交互诊断 LLM：失效分析 → 零训练插件解决方案（核心主线）

> 本文档把整个项目串成一条可复述、可答辩的因果链：**我们先找到一个失效场景，逐层归因到真正的失效环节，据此提出一个零训练插件，并用对照实验证明它解决了问题、且能迁移到其它方法底座上。**
>
> 每一段结论都标注：✅ 干净数字（不依赖"关键证据"定义）/ ⚠️ 已作废数字（依赖旧 confirmatory 定义，待判别性重标注后重算）。
>
> 判分口径：`deterministic_judge`（答案归一化后与 ground_truth 严格匹配），200 例 MedQA × 16 turns × qwen-plus（全角色同模型）。

---

## 0. 一句话结论

**交互式医学诊断的失效不在"诊断器不会看病"，而在"采集器不会定向采证据"。** 我们的插件把这两件事分开、分别修：采集层注入 **8 维证据框架**（扫全证据面）、诊断层加 **CEV-GR 四检查门控**（claim/gap/refutation/decisive 审计闭环），两个组件**可加、零训练、纯 prompt 级**，在 refine 底座上 **+10.0pp**（55.0%→65.0%），在 roleplay 底座上 **+15.0pp**（49.0%→64.0%）。

---

## 1. 研究问题与起点

**场景**：AgentClinic-MedQA 多轮交互诊断 benchmark——医生 agent 在 ≤16 轮内通过 `[QUERY]`（问病史）和 `[TEST]`（下检查）与病人/reporter 模拟器交互，最终给出诊断，判分严格匹配。

**最初的失效观察**：这类交互式诊断方法的三个上游基线在 qwen-plus 上准确率都低——roleplay **49.0%**、refine **55.0%**、sc **59.0%**，远低于"开卷考试"（把病例全部信息一次喂给模型、单次 CoT 诊断，`cot` 上界 **85.5%**）。

**要回答的核心问题**：这 26–36pp 的落差，**丢在哪一环**？是"模型不会从证据推出诊断"（诊断层），还是"模型没在对话里问到该问的证据"（采集层）？——这个问题不定位清楚，任何改进都是瞎试。

---

## 2. 失效场景定位：oracle 上界实验 ✅

**方法**：固定**同一个** qwen-plus 诊断器、**同一个** prompt，唯一变量是喂给它的证据。开卷喂不同档证据，测诊断器在不同证据完备度下的上界。

| 证据喂法 | 准确率 | 状态 |
|---|---|---|
| oracle_full（喂病例全部事实） | **87.5%** | ✅ 干净 |
| oracle_exam（只喂检查结果） | **70.5%** | ✅ 干净 |
| oracle_key（喂"关键事实"） | 80.0% | ⚠️ 作废（见 §3.4） |
| 交互式采集（refine 基线） | 55.0% | ✅ 干净 |

**结论 1（诊断器非瓶颈）**：喂完整证据，诊断器能到 **87.5%**——它"会看病"。失效不在诊断层。

**结论 2（失效在采集层）**：交互式采集 55.0% vs oracle_full 87.5%，**约 32.5pp 的差距干净地归因到采集层**——医生在对话里没采到足够的证据。

> 这套"开卷喂证据测诊断器上界"的做法是**方法级贡献**：它不依赖任何"关键证据"定义，因此结论干净、可迁移到任何交互诊断系统做瓶颈定位。

## 3. 失效根因的逐层分析（一条"证伪链"）

定位到采集层只是第一步。接下来每一步都在**排除一个错误解释**，逼近真正机制。这条链的每一步都曾得出一个假设，再被下一个实验证伪或坐实。

### 3.1 行为分析：查什么 ≠ 查多少

对比"基线"（查得最多）和"方案A"（查得更少）的行为统计，发现一个反直觉事实：

| 医生行为 | 基线 | 方案A |
|---|---|---|
| 检查占比（check 次数） | **66.9%（最多）** | 42.1%（更少） |
| 关键检查覆盖率 | 42.3% | **61.1%**（更高） |

**结论**：不是"查得不够多"，是**"查得不对"**——基线狂下常规/噪音检查（体温、血压、血常规），方案A 下判别性检查（ptosis、肌力、抗体）。真正的瓶颈是"噪音检查 vs 判别检查"的选择。

> ⚠️ 上表覆盖率数字依赖旧"关键检查"定义（见 §3.4），但**"查什么≠查多少"的定性结论独立成立**。

### 3.2 过程归因：环境瓶颈假说

回看每个 case 每一轮的 `[THOUGHT]`（模型当时可观测的推理），对"没采到的关键检查"做**过程归因**（而非站在答案反推）：

- **env_unavailable 61.9%**：医生请求了检查，但 reporter 返回 "Not specified"（closed-world 逐字检索，面板里没有就返回空）。
- 方向没想到（真知识缺口）仅 **9.4%**。

**当时的假设**：主战场是"环境瓶颈"——关键检查不在检查面板里，reporter 不给结果，医生想查也查不到。

### 3.3 面板补全实验：证伪环境瓶颈 ✅（干净负结果）

把 200 例检查面板全部补全（exam_facts 从 14.87 条/例 → 39.5 条/例），消除"查不到"的人工瓶颈，再重跑方案A：

| 指标 | 稀疏面板 | 补全面板 | 变化 |
|---|---|---|---|
| **准确率** | 64.5% | 64.5% | **+0.0pp** |
| 检查命中率 | 27.4% | 48.5% | +21.1pp |
| 每例采到检查 | 7.6 条 | 14.3 条 | +88% |

> 注：本批方案A 为 64.5%（129/200），与最终 §5 的 65.0%（130/200）差 1 例，属不同批次判分噪声，不影响"+0.0pp"结论。

**结论**：环境瓶颈缓解了（命中率 +21pp），但准确率**纹丝不动**。说明 env_unavailable 统计占比虽高，但**不是诊断失败的因果瓶颈**——多采到的检查几乎全是噪音。§3.2 的"环境瓶颈"假设**被证伪**。

> 这是一个干净的负结果：它排除掉了"面板稀疏"这个干扰项，把问题**重新钉回"定向采集"**——不是"查不到"，是"没查对方向"。

### 3.4 度量批判：confirmatory → discriminating ⚠️

到这里必须停下来质疑**度量工具本身**。之前所有"关键检查覆盖率"数字，都依赖一份 `key_facts.json`，它的标注标准是：

> "Given the correct diagnosis ... identify KEY evidence for establishing that diagnosis"（确诊该病的检查）

**三个结构性缺陷**：
1. **事后开卷**——标注时已知答案，往回标"确诊检查"。
2. **标准错位**——"确诊检查"（confirmatory，最后一锤）≠"判别检查"（discriminating，帮你从候选里筛出正确答案）。
3. **循环依赖**——"确诊检查"天然与"诊断对"强相关，用这个指标解释对错，是同义反复。

**修正方向**（已固化在 `docs/discriminating-key-exam-definition.md`，待三参数拍板后重标注）：

> **判别性关键检查**：给定「主诉+病史」确定的鉴别诊断候选集 S（含正确答案 D*），检查 e 是"关键"的，当且仅当 **e 的结果在 D* 与 S 中至少一个竞争诊断之间产生不同预期**（能提供区分证据）。

并拆成两个正交指标——**方向命中率**（正确诊断进没进 top-k 候选）与**判别检查覆盖率**（方向对的前提下采没采到判别检查）——把"想没想到"和"选没选对"分开。

**影响范围**：oracle_key 80%、关键检查覆盖率 42.3%/61.1%/59.6%、过程归因的 env_unavailable 占比，**全部作废待重算**。oracle_full 87.5% / oracle_exam 70.5% / 面板补全命中率 **不受影响，保持干净**。

> 这条度量批判**本身是本项目最硬的方法论贡献**——它戳的是评测通病，且给出可执行的解药（判别性定义 + 指标正交化 + 反例检验判据）。

## 4. 插件设计：双组件、零训练、纯 prompt 级

归因收敛后，插件是两个**正交组件**，分别对应上面定位的两个环节：

| 组件 | 层 | 改动 | 锚点 |
|---|---|---|---|
| **8 维证据框架 + 去效率** | 采集层 | doctor prompt 三处替换 | 证据类别缺口（cover） |
| **CEV-GR 四检查门控** | 诊断层 | claim / gap / refutation / decisive 验证环 | 诊断假设对（verify） |

**采集组件**的三处改动：
1. 去掉 `"Efficiency: ... as few turns as possible"`（它鼓励少问、窄问、快结束）；
2. `efficiently gather` → `comprehensively gather`（措辞一致化）；
3. 注入 8 维证据框架：主诉/现病史/伴随症状/既往史/用药史/社会职业暴露史/查体/实验室影像，FINISH 前必须系统覆盖。

**诊断组件**：CEV-GR 验证环对诊断器的输出做四步审计（claim 核对、gap 补问、refutation 反证、decisive 裁决），缺证据就 `GATHER` 回采集。

**关键设计判断**：采集组件的锚点是**"证据类别缺口"（静态清单）**，不是**"诊断假设优先级"（动态排序）**。这个区分是后面所有负结果/正结果的分水岭（见 §6）。

## 5. 解决效果：方案A +10pp，跨底座泛化 ✅

完整插件（8维框架 + CEV-GR）在 refine 底座上：

| 方法 | 准确率 | vs refine 基线 |
|---|---|---|
| refine（论文原版，无 CEV-GR） | 55.0% | — |
| **refine_cv_cover（方案A = 完整插件）** | **65.0%** | **+10.0pp** |

**跨底座泛化**（把完整插件原样移植到其它方法底座，只覆写 doctor prompt 与 finish 动作）：

| 底座 | 原样 | +CEV-GR | +8维框架(无CEV-GR) | 完整插件 | Δ vs 原样 |
|---|---|---|---|---|---|
| **refine** | 55.0% | 58.5% | 60.0% | **65.0%** | +10.0 ✅ |
| **roleplay** | 49.0% | 57.5% | 53.5% | **64.0%** | **+15.0** ✅ |
| sc | 59.0% | 58.5% | 56.5% | 65.0% | +6.0 ⚠️ |
| react | 53.0% | 46.5% | — | 50.0% | −3.0 ❌ |

- **roleplay 底座大胜**：从 49% 拉到 64%，几乎追平 refine 底座——插件在"采集-诊断解耦"底座上**稳定生效**。
- **sc 底座暴露诊断管线依赖**：8维框架单独 −2.5pp（见 §6）。
- **react 底座结构性不兼容**：完整插件 −3.0pp（见 §6）。

## 6. 消融与机制：可加性、管线依赖、适用边界 ✅

### 6.1 可加性（refine 底座消融链已闭合）

```
refine 55.0% ──+CEV-GR(+3.5)──► refine_cv 58.5%
                                  └─+去效率(−1.0)──► freebudget 57.5%
                                  └─+去效率+8维框架(+6.5)──► 方案A 65.0%
refine 55.0% ──+去效率+8维框架(+5.0)──► refine_cover 60.0%
refine_cover 60.0% ──+CEV-GR(+5.0)──► 方案A 65.0%
```

| 组件 | 独立贡献 | 测量方式 |
|---|---|---|
| 8 维框架 | **+5.0pp** | refine 55.0 → refine_cover 60.0（无 CEV-GR 底座） |
| CEV-GR 四门控 | **+5.0pp** | refine_cover 60.0 → 方案A 65.0（cover 底座） |

**结论**：两组件**近似可加**（5.0 + 5.0 = 10.0），不是协同依赖。且 `freebudget`（只去效率、不加框架）=−1.0pp，证明**"去效率"本身无益甚至略有害，8维框架才是采集组件的主贡献**——单纯"多问"没用，必须给医生一份"覆盖什么"的清单。

**roleplay 底座同样闭合**（本次补跑 `roleplay_cover_abl`）：

```
roleplay 49.0% ──+8维框架(+4.5)──► roleplay_cover_abl 53.5%
                                     └─+CEV-GR(+10.5)──► roleplay_cover 64.0%
roleplay 49.0% ──+CEV-GR(+8.5)──► roleplay_cv 57.5%
```

8维框架在 roleplay 上的独立贡献 **+4.5pp**，与 refine 底座上的 +5.0pp **基本一致**——再次坐实"8维框架是底座无关的采集组件"。且 roleplay 上两组件单独贡献之和（+4.5 + +8.5 = +13.0）< 完整插件（+15.0），存在约 **+2.0pp 的正协同**（弱基线补短板时协同更明显）。

### 6.2 采集组件的"诊断管线依赖"（sc 底座，最锋利的发现）

```
refine 管线（验证环）:  55.0% ──+8维框架──► refine_cover 60.0%   (+5.0pp)
SC  管线（summarizer）: 59.0% ──+8维框架──► sc_cover 56.5%       (−2.5pp)
```

同样的 8 维框架采集改动，在 refine 验证环管线上 +5.0pp，在 SC 的"summarizer→diagnostician 一步诊断"管线上 **−2.5pp**。机制：8维框架让医生多采广覆盖证据（含噪音），refine 验证环能按"缺口"定向消化，SC summarizer 把证据一锅端、反而**稀释了关键信息**。

**结论**：8维框架不是"纯采集增益"，它的收益**依赖诊断层的验证环来消化**。这解释了为什么方案A = 8维框架 + CEV-GR **必须成对出现**（一个采、一个消化）。

### 6.3 适用边界（react 底座 + 6 个负结果）

**react 底座**：`react 53.0% → react_cv 46.5% → react_cover 50.0%`。8维框架部分缓解了 CEV-GR 的 give_up 损伤（+3.5pp），但"采集-诊断单 agent 耦合 + [DIAGNOSIS] 即终点"的结构性冲突主导，救不回来。**适用边界 = 采集-诊断解耦底座**。

**采集层负结果规律**（P0 −4.5 / P0P1 −6.5 / 两阶段 K4/6/8 / 方案B / 去偏置 / 方案C1 −3.5，统一失败）：

> **LLM 采集器无法可靠执行"动态优先级/选择"，任何"优先级、选哪些假设/证据先问"的措辞都会退化成"少问、快结束"。唯一有效的是"静态完整清单"范式。**

这是 6 负 + 1 正共同锁定的清晰边界，本身有发表价值（"what doesn't work"）。

## 8. 这条链的方法论价值（可迁移）

1. **oracle 上界框架**：任何交互诊断系统，用"开卷喂证据测诊断器上界"即可定位瓶颈在采集层还是诊断层——不依赖任何关键证据定义。
2. **度量批判三件套**：判别性定义（检查能否筛掉竞争诊断）+ 指标正交化（方向命中率 vs 判别覆盖率）+ 反例检验判据（用"采到却错+没采却对"的反例占比证明度量没循环）。适用于所有用"证据覆盖率"做诊断评测的工作。
3. **静态清单 > 动态优先级的采集范式**：6 负 1 正锁定的边界，对 prompt 级采集改进有直接指导意义。
4. **双组件插件定位**：采集组件（8维框架）+ 诊断组件（CEV-GR）可加，但采集组件依赖诊断组件的验证环——这个因果链有 refine/roleplay（正）+ sc（管线依赖）+ react（负）三个方向证据钉死。
